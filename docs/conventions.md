# Conventions — daybreak-decomp

> Living document. Technical decisions live here; pipeline structure
> lives in `docs/pipeline.md`. Translated from the original Portuguese
> `docs/archive/conventions.md` (authoritative if they conflict — but
> they shouldn't; fix drift when found).

## 1. Language standard (by zone)

- **`research/` is C11** (`-std=c11`).
- **`remake/foundation/` is C++17** (`CMAKE_CXX_STANDARD 17`, with
  `CMAKE_C_STANDARD 11` alongside) over SDL3 + WebGPU.
- Rationale for C11 in research: `//` comments, declarations anywhere in a
  block, `stdint.h`, `_Static_assert`, anonymous unions.
- No bit-matching against the original binary is attempted.
- §§2–5 below are research/recomp conventions (`PascalCase` funcs,
  `FUN_<addr>` for unreviewed) unless a rule explicitly applies to the
  foundation — product contributors follow the foundation's C++17, not C11.

## 2. Types

- Fixed-size integers from `stdint.h`: `uint32_t`, `int32_t`, `uint8_t`, etc.
- Win32 types keep Windows typedefs: `HWND`, `HMODULE`, `DWORD`, `BOOL`.
- Direct3D types keep D3DX names: `D3DXVECTOR3`, `D3DMATRIX`, etc.

## 3. Formatting

- `.clang-format` at the repo root, LLVM style with 4 spaces.
- Applied automatically by `research/tools/generate_recomp.py`
  (via `clang-format --style=file`, resolved from the working directory).
- Nobody formats by hand — if the output displeases, adjust
  `.clang-format`, not the code.

## 4. Naming

### 4.1 Functions
- `PascalCase` for renamed functions (`LoadNextScene`, `CommonInit`).
- `FUN_<addr>` for unidentified functions (preserve the original address).
- Never snake_case for functions (keeps Win32 / DirectX style).

### 4.2 Variables
- `snake_case` for locals (`count`, `scene_id`, `next_state`).
- `g_<name>` for globals (`g_game_state`, `g_d3d_device`).
- `m_<name>` for struct members (COM/Hungarian-lite style).

### 4.3 Structs
- `PascalCase`, with a `_T` suffix when it collides with Win32
  (`GameState`, `SceneHandler_T`).
- Fields in `snake_case`.

## 5. Comments

### 5.1 Function header (generated by `generate_recomp.py`)
```c
// ============================================
// Address:  0x00406310
// Original: FUN_00406310
// Name:     LoadNextScene (status: reviewed)
// ============================================
```

### 5.2 TODOs
- `// TODO(decomp): <description>` — unresolved decompilation ambiguity
- `// TODO(recomp): <description>` — recomposition debt (e.g. missing struct)
- `// NOTE: <description>` — useful observation, no pending action

### 5.3 Traceability markers
- When renaming a function, always keep `// Original: FUN_<addr>` in the header.
- If the function came from an extraction-agent suggestion (plate comment
  in Ghidra), include `// Suggested by: agent:extraction`.

## 6. Commit conventions

### 6.1 Prefixes
- `feat:` new decompiled function or new phase
- `fix:` fix to an existing file
- `docs:` report or progress update
- `chore:` config tweaks (`.gitignore`, scripts)
- `refactor:` rename or reorganization
- `recomp:` reserved for automatic recomp-pipeline commits
- `symbols:` changes to `research/symbols/*.json`

### 6.2 Direct push to `main`
- ✅ `research/decompiled/*.c`
- ✅ `research/binary_data/*`
- ✅ `research/symbols/*.json` (with human review)
- ✅ `research/progress/*`
- ✅ `*.md`, `research/extraction_phases/*.txt`
- ❌ `research/recomp/*.c` — only via `research/tools/generate_recomp.py`
  (automatic commit) or manual PR after review

## 7. Branches

- `main`: primary branch, always in a sane state
- `recomp-auto`: automatic pipeline branch (no manual work there)

## 8. When a function may NOT be renamed

Status `unreviewed` or `stale` → keep `FUN_<addr>` in the code.
Put the suggestion in a comment only:
```c
// suggested name: ParseAnimationHeader (confidence: medium, status: suggested)
void FUN_00401230(int param_1, char *param_2) {
```

## 9. When a function MAY be renamed

Status `reviewed` or `locked` → free to rename.
Keep traceability via the header:
```c
// ============================================
// Address:  0x00406310
// Original: FUN_00406310
// Name:     LoadNextScene (status: reviewed)
// Suggested by: agent:extraction
// Reviewed by: marcelo
// ============================================
uint __fastcall LoadNextScene(GameState *state) {
```

## 10. When a function goes stale

If `signature_hash` changes (the function was re-decompiled with a
different result):
- Status returns to `stale`
- Automatic comment in `notes.json` describing what changed
- Re-review required before returning to `reviewed`/`locked`
