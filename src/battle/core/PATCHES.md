| 2026-11-04 | None: `src/battle/core_prelude.h`, force-included | The core's `_mm_rsqrt_ss` and `_mm_rcp_ps` resolve by macro to `det_rsqrt`/`det_rcp` in the new `src/battle/det_estimate.c`, the exactly rounded `1/sqrt(x)` and `1/x`. Headers stay as vendored. **This is a deliberate behaviour change:** the estimate they replace is the CPU model's, so every affected path now computes one value everywhere instead of this machine's. Two SIM fingerprints and one PIX move; see below | **Failure:** issue #107. Two machines in one online room desynced on 3277 and 3319 of 3600 frames, first at frame 181-182, on every run and for every seed, while two peers on either machine alone agreed. **Cause, tier 5, measured on a Ryzen 5 5600 (Zen 3) and an i3-10100T (Comet Lake) with one binary:** SSE specifies `rsqrtss` only to within 1.5*2^-12, and the bits it returns are a per-model table. A sweep of `1..2e6` digests `00bbea513765195f` on one and `08f27ffa2a95fa4c` on the other; worst relative error 2.58e-4 vs 3.25e-4; and after the single Newton step the answer still misses the exactly rounded one on 33% of inputs there and 40% here. `actor_controller_normalize3`/`normalize4` start from it, so the two peers' normalised vectors parted in the last bit. Isolated with `simctl --hash-log` on both machines, same command, no network: first differing tick 181. Per-field digests of `Battle::visit_state_fields` (120 fields) named exactly one: `world.actors[3].relationships.target` — a target switch tipping the other way, with no visible row or hit change. Restored by the cross-machine `simctl` comparison in `docs/NET-TWO-MACHINE.md`. `_mm_rcp_ps` in `actor_skin.hpp` is the same hazard in `transform_point`; it reaches only the rendered skin, never `stateHash`, so it was a visible-only divergence, fixed with it. A core-wide survey found no other vendor estimate and no `-ffast-math`. Regression: `math_accuracy_test` holds both functions to the exactly rounded value over 1.9M inputs, and reintroducing either estimate fails it (1,944,593 mismatches measured). Fingerprints moved, as intended: SIM `5331c6e70cd13962`→`941f3dcd7a679d74` and `e79f1dbb68d73853`→`f19e8d6d58c37151`, PIX `title4p` `8ebdbd62`→`9ecda8ec`; SIM `rena-mion-keiichi-satoko` (`746ce7a9cbe6e44a`) and PIX `battle640`/`title720` did not. Before this change the other machine computed `39d764815e8f586a` and `5502dccfcc2787e4` for those two rosters, so those "regression hashes" only ever held on one CPU vendor; after it both machines compute the new values |
